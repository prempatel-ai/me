A Small Task Queue That Survives Crashes

Oct 24, 2025 · 4 min read

A system that keeps working even when things break.

Most queue tutorials show you how to push a message into memory and pop it in a worker thread. But what happens when the power gets cut midway? Notes on building a small, resilient job queue with SQLite, leases, and idempotency.

Most tutorials on queues make everything look easy. You set up a broker, push a message in, pop it out in a worker, and print “job done.”

In practice, that only works when nothing goes wrong. In the real world, servers restart unexpectedly, memory runs out, network calls hang, and worker processes get killed right in the middle of writing a file.

When that happens, what happens to the job? Does it vanish into thin air? Does a worker wake up, see the job half-finished, and run it again? If that job was charging someone's credit card or writing a transaction to a ledger, running it twice is a serious problem.

I wanted to see what it actually takes to build a queue that survives crashes without needing a giant distributed setup. Just a simple system where every submitted job always reaches a definitive end: either “completed” or “failed”, no matter who crashes along the way. And if a job runs twice, you still get one clean, correct result.

“A reliable system is not one where nothing crashes. It is one where crashes do not corrupt the outcome.”

The job

To test this without getting bogged down in application details, I picked a simple deterministic job:

“Count the words in a text file and save the count.”

Deterministic means if you run it ten times on the same input file, you get the exact same word count all ten times. That predictability makes it easy to verify whether a retry gave you the right answer or corrupted something along the way.

The four pieces

I kept the architecture down to four straightforward components:

1. API: The front desk. It accepts a job request, assigns a job ID, and returns it to the client immediately.

2. Coordinator: The central brain. It keeps track of every job's status in a SQLite database persisted on disk. Not in temporary memory where a restart wipes everything out.

3. Workers: The hands. They ask the coordinator for an available job, process it, write the result, and report back that they are done.

4. Result store: A dedicated table on disk where each result is saved directly under its job ID.

The rules that keep it alive

Building the happy path took an afternoon. Getting the failure modes right took much longer. These are the rules that make the whole system survive crashes:

No double jobs (Idempotency). Clients retry requests when connections drop. If a client submits a job, doesn't hear back because of a network blip, and sends it again, you do not want two identical jobs queued up. Every submission carries a unique key. If the API sees a key it already knows, it doesn't create a second job. It just returns the existing job ID.

Time limit and leases. When a worker picks up a job, it does not own it forever. It gets a lease with a strict time limit. If the job takes longer, a healthy worker sends a heartbeat signal saying “I am still working” to extend it. Crucially, only the coordinator's clock decides when time is up, preventing worker clock drift from breaking the system.

Retries and backoff. If a worker crashes silently and its lease expires, the coordinator returns the job to the queue. But we don't retry immediately. The wait grows after each attempt. Also, we count an attempt the moment a job is picked up by a worker, not when it fails. If a job fails three times, we stop retrying and mark it “failed”.

No duplicate results. What if a worker gets slow, its lease runs out, and a second worker picks up the same job? The slow worker might finish a few seconds later and try to submit its result. The rule is simple: marking a job “completed” only succeeds if the job is not already completed. The first valid result wins, and later submissions are safely ignored.

Backpressure. If thousands of jobs arrive faster than workers can finish them, an unbounded queue will eventually exhaust disk space and memory. When the waiting queue hits its limit, the API stops accepting new jobs and immediately returns HTTP 429 (“Too Many Requests, try later”). It is much better to reject new work honestly than to let the server crash under load.

Security. Workers talk to the coordinator over HTTPS, and each worker authenticates using a secret token. Only recognized workers can lease jobs or submit results.

The chaos checklist

Writing the code is only half the work. The fun part was actively trying to break it. I set up automated tests that deliberately pull the rug out from under the system:

• Kill a worker mid-job: The lease expires, the coordinator puts the job back in the queue, another worker picks it up, and the job ends as completed.

• Kill a worker after saving the result but before telling the coordinator: The retry runs, the second worker finishes, and because the write is idempotent, there is still exactly one correct result.

• Slow worker race condition: A worker finishes after its lease expired, while a second worker already started the job. The first result wins, the second is ignored, and no state is corrupted.

• Kill and restart the coordinator: Because state lives in SQLite on disk, when the coordinator boots back up, every job's status is still completely intact.

• Submit the same job key twice: The API returns the original job ID without creating a duplicate task.

• A job that always crashes: A poisoned task that crashes any worker running it gets retried three times, exhausts the max tries, and ends as “failed” instead of looping forever.

• Traffic flood: Sending jobs faster than workers can finish. The API immediately responds with 429 backpressure without crashing.

What I learned

Before building this, distributed systems always felt like an abstract wall of theory and heavy buzzwords.

Building a small queue from scratch showed me that reliability isn't magic. It is just being honest about how things break. Network packets get dropped. Processes get killed without warning. Machines run out of memory.

Once you accept that crashes are normal events rather than rare exceptions, designing around them becomes an interesting puzzle. You stop assuming that “if I told the worker to run it, it will finish”, and you start asking “what happens if it dies halfway through?”

I'm still refining the code, but seeing the whole checklist pass while pulling processes down felt really satisfying.
